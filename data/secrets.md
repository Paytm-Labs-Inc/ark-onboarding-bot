Check this table before you paste anything.
Credential| Looks like| Where it comes from| What it is for  
---|---|---|---  
**User API key**| `ark_t-<tenant>_<hex>`| Settings, then API Keys| Everything you do as yourself: the MCP config, `ark login`, `curl` against `/api/rpc`  
**Worker token**| `ark_t-<tenant>_<hex>`| Minted by the enroll card or `ark host enroll`| Only the machine uses it. `auth/whoami` reports `"role":"worker"`  
**Slack link token**|  32 hex characters| `ark slack link`, or the Connect Slack card| Single use, expires in 15 minutes, DM'd to the bot  
**Session secrets**|  Varies| The secrets on this page| Consumed inside a session by the agent, never by you  
A user API key and a worker token are the same shape, which is why they get mixed up. If you are about to use a key yourself, it must be a **user** key. Verify with the `auth/whoami` check on the [troubleshooting page](/onboarding/troubleshooting#the-api-key-is-rejected).
Name your keys for their purpose
The key name is the only thing distinguishing them later, and the default suggestion is the same for every key you mint. Name them for the job: `mcp-<yourname>`, `cli-<yourname>`, `enroll-<box>`.
## What to set 
Name| Value| Where to get it  
---|---|---  
`JIRA_USER_EMAIL`| your email| -  
`JIRA_API_TOKEN`| Atlassian API token| <https://id.atlassian.com/manage-profile/security/api-tokens>  
`ATLASSIAN_BITBUCKET_USERNAME`| your Bitbucket **username** , not your email| <https://bitbucket.org/account/settings/>  
`ATLASSIAN_BITBUCKET_APP_PASSWORD`| an app password. Grant Repositories Read+Write and Pull requests Read+Write| <https://bitbucket.org/account/settings/app-passwords/>  
`BITBUCKET_SSH_KEY_<WORKSPACE>`| dedicated SSH private key. The suffix matters: see below| generated by you  
`ARK_GIT_AUTHOR_NAME`| the name you want on commits| -  
`ARK_GIT_AUTHOR_EMAIL`| the email you want on commits| -  
`CLAUDE_CODE_OAUTH_TOKEN`| Claude OAuth token| `claude setup-token`  
### The two that surprise people 
**`ARK_GIT_AUTHOR_NAME` and `ARK_GIT_AUTHOR_EMAIL` decide who your commits belong to.** Leave them unset and commits are attributed to a generic agent identity rather than to you, which is not something you can fix after the fact without rewriting history. Set them before your first real run.
**`CLAUDE_CODE_OAUTH_TOKEN` is not optional in practice.** Workspaces that run a Claude-based agent declare it, and a workspace that declares a secret which does not resolve fails at dispatch, before the agent starts. Mint one with `claude setup-token`. It is an OAuth token, so it expires: a lapsed token reports as _missing_ , not as expired, which is why a setup that worked yesterday can fail today with no change from you.
If you do not have Claude access, you can dispatch against the Cursor runtime with `CURSOR_API_KEY` set instead. Selecting a runtime does not change what the **workspace** requires, so a workspace that declares `CLAUDE_CODE_OAUTH_TOKEN` still demands it on a Cursor run.
### Values your workspace usually provides 
`JIRA_SITE_NAME` and `BITBUCKET_DEFAULT_WORKSPACE` identify which Atlassian site and which Bitbucket workspace to talk to. Most workspaces set them, so you normally do not.
`JIRA_SITE_NAME` wants the **subdomain only** , not a URL: `mypaytm`, or `paytmmoney` for Paytm Money. If your Jira integration cannot find anything, this is the first value to check.
Do not set these at user scope
`JIRA_BASE_URL`, `JFROG_USERNAME`, `JFROG_PASSWORD`, or anything else infra-flavored. They are shared configuration, and a user-scope override becomes invisible per-person drift that reads as "Foundry is broken only for me".
## How scope resolution works 
Secrets resolve **narrowest first** : user, then team, then tenant, and the first hit for each name wins. A team that sets nothing inherits the tenant default.
Two consequences worth knowing before you debug a missing secret:
  - Setting a value at **user** scope overrides team and tenant for your sessions only. That makes it the fastest way to unblock yourself while a shared value is being sorted out.
  - A team-scoped secret is matched by the team's canonical `tm-` id. A value stored against the team's name or slug will be visible in the UI and still not resolve at dispatch.

## Updating or rotating a secret 
You do not need to delete a secret to change it. Adding it again with the **same name and the same scope** replaces the value. Tokens that rotate on a schedule, such as an Atlassian API token or a Claude OAuth token, are re-set exactly this way.
## Bitbucket SSH key 
The suffix on `BITBUCKET_SSH_KEY_<WORKSPACE>` names the **Bitbucket workspace** the key unlocks, and it is not decoration. Match it to where your repos live:
Secret name| Unlocks| Use it if your repos live at  
---|---|---  
`BITBUCKET_SSH_KEY_PAYTMTEAM`| the `paytmteam` workspace| `bitbucket.org/paytmteam/...`  
`BITBUCKET_SSH_KEY_PAYTMMONEY`| the `paytmmoney` workspace| `bitbucket.org/paytmmoney/...`  
Setting the wrong one produces `Permission denied (publickey)` at clone time, which reads as an unauthorized key rather than an absent one. Check the URL of a repo your workspace clones and match the suffix to the segment after `bitbucket.org/`.
Use a **dedicated, passphrase-free** key. Do not reuse your personal key: a session cannot type a passphrase, and a dedicated key is revocable without breaking your laptop.
**Step 1. Generate:**
bash
    
    ssh-keygen -t ed25519 -C "ark-bitbucket-$(whoami)" -f ~/.ssh/ark_bitbucket -N ""
The `-N ""` is required. A passphrase-protected key hangs every clone forever.
**Step 2. Register the public half with Bitbucket:**
bash
    
    cat ~/.ssh/ark_bitbucket.pub
Copy that single line, which starts with `ssh-ed25519`, open <https://bitbucket.org/account/settings/ssh-keys/>, add the key and label it `ark`.
**Step 3. Verify before touching Foundry:**
bash
    
    ssh -i ~/.ssh/ark_bitbucket -T git@bitbucket.org
Success reads `authenticated via ssh key. You can use git to connect to Bitbucket.` Anything else means stop and fix this first. Most "Foundry cannot clone" reports are a key that was never valid, and every minute spent on the workspace before this check is wasted.
**Step 4. Put the private half into Foundry:**
bash
    
    cat ~/.ssh/ark_bitbucket
Add a secret with the name matching your Bitbucket workspace from the table above, scope **user** , type **ssh-private-key**. Paste the entire output **including** the `-----BEGIN OPENSSH PRIVATE KEY-----` and `-----END OPENSSH PRIVATE KEY-----` lines. Copy from `cat`, not from an editor that may reflow it.
The five mistakes people make
  1. Pasting the `.pub` file into Foundry. Foundry gets the **private** key and Bitbucket gets the public one. If your paste is a single line, it is the wrong file.
  2. The wrong workspace suffix. `PAYTMTEAM` and `PAYTMMONEY` are different keys for different Bitbucket workspaces.
  3. A key with a passphrase. Regenerate with `-N ""`.
  4. Truncated BEGIN and END lines, or line breaks mangled by an editor. Paste byte for byte.
  5. Skipping step 3.

## Check it worked 
Dispatch is the slow way to find out a credential is wrong. Prove the workspace materialises first, with no agent in the loop:
bash
    
    ark workspace test <workspace> --compute <compute>
This runs the real provision, clone and services phases and tells you which one failed. A clone failure here is a credential problem and names itself as one.
